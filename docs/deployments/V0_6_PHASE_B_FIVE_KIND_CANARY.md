# V0.6 Phase B five-kind canary plan

Status: local design and test preparation only. No production VM shadow or canary is authorized by this document. The [alpha.9 30-minute trial](V0_6_ALPHA9_SHADOW_PRESTART_CHECKLIST.md) remains separately gated and covers only resources, reconnection/gap and one real `ready`. Passing it does not complete Phase B.

## What must match

Compare Sidecar observations with the current patched-Hub durable outbox for the **same namespace, session, event kind and bounded observation window**. Start a fresh canary session after the Sidecar is live, so cold-start baselines and old events cannot be counted as matches. Keep `HAPI_SIDECAR_DELIVERY_MODE=shadow`: Sidecar delivery rows must remain zero, the legacy Relay is the only sender, and Mac/phone bindings stay unchanged. The official SSE is memory-bounded; a gap outside replay can miss any number of ready/task events. Record such a gap as a failed or indeterminate comparison, never as parity.

| Contract kind | Isolated test can prove | Real production canary needed for full Phase B | Expected user/operator action |
|---|---|---|---|
| `ready` | Official-shaped `message-received` fixture, cooldown, deduplication and exact URL | One fresh Runner turn reaching ready, observed by both paths | Operator sends harmless prompt in a dedicated canary session; no user action if separately authorized |
| `session-completed` | `session-ended` with `reason=completed`; abort is excluded; task suppression | Fresh canary session ends **normally** and both paths record completion | Operator may close/end only the dedicated canary session after explicit approval; do not end an existing user session |
| `task-notification` | Both structured task forms, normalization and generic-completion suppression | A real Runner produces a completed background-task notification seen by both paths | Operator starts a harmless bounded child task in the canary session; if the Runner cannot generate this form, mark unverified |
| `permission-request` | New request ID, 500 ms pending confirmation, resolution/replay deduplication | A real pending tool approval is exposed long enough for both paths to observe | User or authorized operator handles a harmless approval in the canary session; never trigger a privileged/destructive tool just to fill the matrix |
| `input-request` | Supported question-tool names and request ID, pending confirmation and deduplication | A real user-input request is exposed long enough for both paths to observe | User or authorized operator answers a harmless canary question; a chat message alone is not this event kind |

The existing local interpreter/source fixtures prove that five **shapes** can be inferred, but cannot prove that the VM's actual Runner emits those shapes or that the patched composer makes the same decision. No synthetic row inserted into a production DB, replayed fixture sent to a production endpoint, or ordinary `test notification` counts as a real canary event. A kind that cannot be generated safely remains **unverified**; it is not silently waived. Full Phase B requires all five real kinds, or a separate product-owner change to the specification.

## Smallest safe sequence after the first trial

1. **Local gate before any second VM request:** keep the frozen alpha.9 binary unchanged; test the five-kind content-free shadow report locally. Review the **read-only, offline comparator** below against synthetic SQLite snapshots, then build its separate Linux executable and verify it in isolation before any VM use. Its future VM inputs must stay private; no raw database, session ID, title, prompt, request text, topic or credential may leave the VM. Local tests alone do not authorize VM access or prove production parity.
2. **Separate shadow authorization:** request a new, bounded VM window and a dedicated canary session. Recheck the same pre-install matched rollback set, exact artifact hashes, private loopback, `Restart=no`, 5% CPU/128 MiB limits, zero delivery rows and stop thresholds from the first-trial checklist. A prior 30-minute PASS does not extend the old authorization. If alpha.9 can remain installed but stopped, verify its identity/state before reuse; do not reinstall blindly.
3. **Observe in order:** mark a new comparison boundary after source `live`; perform ready, input request, permission request, background task and normal session completion in the dedicated session, with one pending request at a time. Record each attempted trigger and whether **both** paths actually produced a candidate. Do not force a rare kind using an unsafe action. Avoid task/completion overlap within the documented ten-second suppression window unless specifically testing that suppression; when overlap occurs, compare the expected suppressed outcome rather than demanding two notifications.
4. **Compare privately:** on the VM, use one fresh random key for both snapshots and HMAC-SHA256 the same session ID; never export the key or either snapshot. Match kind plus fingerprint within the **predeclared 5,000 ms tolerance**, then check one-to-one counts, duplicates and absence of unexpected notifications. Compare request kinds by HMAC of request ID **only inside the private comparator** so two questions/approvals in one session cannot be confused. Compare task/completion suppression explicitly. The 5,000 ms ceiling is based on historical ready-parity maxima around 4.6 s; it needs independent acceptance before VM execution and must never be widened after seeing a mismatch. The current `sidecar-shadow-report` gives only aggregate kind/session counts and no per-event timestamp, so it cannot by itself establish this gate. Event ordering and exact-session URL structure require separate contract evidence; this comparator intentionally does not claim them.
5. **Record only a summary:** five rows of PASS/FAIL/UNVERIFIED, side-specific counts, match/mismatch counts, timing distribution, gap/reconnect state, resource measurements, zero delivery-row proof, and the comparator/artifact hashes. Small canary populations can be reidentified even from stable fingerprints, so do **not** include fingerprints in the exported report. Delete temporary comparison key, snapshots and detailed report after recording the outcome; retain only the non-sensitive summary and ordinary rollback evidence.
6. **Stop and restore:** stop Sidecar, verify port 8791 closes, preserve the legacy Relay as sole sender, and apply the matched old-Sidecar restore checks from the runbook if installation/state was changed. A mismatch, ambiguous duplicate, official replay gap, source attention, delivery row, health/resource regression or unsafe request immediately ends the canary as FAIL/UNVERIFIED. Do not switch clients or patch pins to “see if it works.”

The comparator uses each store's `created_at` (the emitted notification time), not the source event timestamp, and accounts for the patched path's own enqueue delay. A late or missing patched notification is not automatically a Sidecar failure: investigate privately and report the mismatch as unresolved. HMAC fingerprint equality alone also does not prove per-event parity. The current report's `highWaterSeq` is only the Sidecar's local sequence, not a shared event identity or a patched-outbox ACK cursor.

### Offline comparator contract and remaining gate

`relay/src/phase-b-compare-cli.ts` reads **two already-consistent SQLite snapshots** and a private key/**sealed** source-continuity journal. It opens both databases read-only, queries only `canonical_notifications`, `source_binding` and `companion_notification_outbox`, and never connects to HAPI or a network endpoint. All four inputs must be owned by the process user, private to group/others (`0600` for ordinary files), and absolute regular files. Invocation shape on a local synthetic fixture is:

```text
bun run relay/src/phase-b-compare-cli.ts SIDE_SNAPSHOT HUB_SNAPSHOT KEY_FILE CONTINUITY_JOURNAL.sealed FROM_MS THROUGH_MS 5000
```

The earlier hand-written continuity JSON is no longer accepted by the CLI. An **opt-in, source-owned** `SourceContinuityJournal` now records content-free `run-start`, connecting, official `connected-ok|connected-gap`, live, heartbeat, disconnect, attention and stop transitions. Each private append is fsynced and chained to the previous entry's hash. It writes no session/event ID, notification text, topic or credential, and does not poll HAPI or change the Sidecar database schema. Only after a successful fsynced stop does it atomically rename the file to `.sealed`; a write/sync failure leaves an unsealed file that the comparator rejects. The directory rename is not separately fsynced: if a crash loses the name, evidence becomes unavailable, rather than creating a valid but unconfirmed heartbeat. Stop the source, then take the consistent database snapshots and compare. The comparison tool validates the whole sealed chain, then derives coverage only when one process run was live before `FROM_MS`, remained uninterrupted, every successive heartbeat was at most ten seconds apart, and a heartbeat followed `THROUGH_MS` within ten seconds. A gap, disconnect, restart, long heartbeat silence, bad permissions, partial/tampered entry, missing heartbeat or unverifiable interval returns `INDETERMINATE`. The Sidecar SQLite snapshot must also report live with no attention code. The chain guards against accidental omission/corruption within the service-owned file; it is not a cryptographic attestation against an operator who controls that file.

This journal is **not in the frozen alpha.9 x86_64 archive**. New source code enables it only when a future, separately reviewed Sidecar candidate sets `HAPI_SIDECAR_CONTINUITY_PATH` to a private file under its own state directory. It is a bounded canary recorder, capped at 128 KiB and writing one fsynced heartbeat every five seconds while live; it must not be left enabled indefinitely or silently rotated. Neither the current 30-minute shadow authorization nor a local ARM build authorizes replacing that frozen package or changing the VM unit/environment. The new candidate needs package identity, rollback and measured write/resource gates before any VM trial; until then full Phase B remains open. Stop and seal the journal before comparison, then take a consistent Sidecar SQLite snapshot; if either is missing, do not synthesize a `gapCount:0` file. A failed run's unsealed file remains private for bounded local diagnosis and must be removed during cleanup.

### Continuity recorder storage and authorization proposal

This section describes a **proposed VM activation**, not an authorized installation. The local implementation already exists on the PR branch, but it is default-off and is not part of frozen alpha.9. Do not infer production approval from local tests or from this document. No HAPI or Sidecar SQLite schema change is needed.

| Item | Exact proposed boundary |
|---|---|
| Write path | Set `HAPI_SIDECAR_CONTINUITY_PATH=/var/lib/hapi-companion-sidecar/phase-b-continuity.jsonl` only for a separately authorized, bounded shadow run. This is a new file in the Sidecar's existing `ReadWritePaths=/var/lib/hapi-companion-sidecar`, not in the HAPI DB, Relay JSON or Sidecar SQLite. The current unit/environment file is unchanged. |
| Read path | After a successful stop the writer renames that file to `/var/lib/hapi-companion-sidecar/phase-b-continuity.jsonl.sealed`; the offline comparator accepts only this private sealed file, plus separately created, consistent Sidecar/Hub SQLite **snapshots** and one temporary comparison key. It does not write either database or call the Hub API. No production snapshot read is authorized yet. |
| Fields | Each JSONL entry contains exactly `version=1`, monotonic line `seq`, random process `runId`, millisecond wall-clock `at`, transition `kind`, previous-entry SHA-256 `prev`, and this-entry SHA-256 `hash`. `kind` is one of `run-start`, `connecting`, `connected-ok`, `connected-gap`, `live`, `heartbeat`, `disconnect`, `attention`, `stop`. There is no session/event/request ID, message, title, URL, namespace, topic or credential. The hash chain detects accidental damage; it does not authenticate a file against its owner. |
| Permissions | Parent directory and journal must be owned by the Sidecar service UID and inaccessible to group/others (directory `0700`, file `0600`). The writer uses append and no-follow open, checks ownership/mode/size, and fsyncs every entry. The read-only comparator checks absolute paths, regular files, ownership and private modes. Do not relax the systemd sandbox or add another writable directory. |
| Bound and cleanup | Maximum journal size is 128 KiB; no rotation or silent truncation. Enable only during the approved canary, stop and seal after the end heartbeat, make the needed private consistent snapshots, run the comparator, retain only non-sensitive verdict/count/timing and artifact hashes, then remove both the active and sealed journal paths, temporary snapshots and comparison key under a named cleanup step. On abort, first record only the non-sensitive failure reason, then perform the same cleanup after any authorized local investigation; verify both paths are gone and the environment setting removed. A subsequent start with an old sealed file at the same path is deliberately rejected; never delete that evidence implicitly to make startup pass. Existing matched Sidecar rollback materials remain governed by the separate pre-start checklist. |
| Runtime effect | With the variable unset, no journal is opened, no heartbeat timer runs and no new file is written. With it set, the Sidecar adds one fsynced append per transition and every five seconds while live; startup fails if the private path is unsafe, and write/full/clock failures can stop source observation or put it in attention. This may increase disk writes and alter shadow availability. Delivery must stay disabled; it does not change Hub/Runner, notification clients, public routing, ACK or replay. A new binary/environment is nevertheless a deployment behavior change. |

Before any VM use, independently review the implementation and exact Linux x86_64 package, measure the journal's CPU/RSS/write/fsync cost under a resource limit, prove normal and fail-closed paths with synthetic data, record the old package/config/state rollback set, and obtain explicit approval for the new artifact, environment setting, duration, resource limits, stop conditions and cleanup. If approval is not granted, keep frozen alpha.9 and the current notification path; the local comparator cannot claim trusted live continuity from a hand-written file.

**Independent review and remaining gate (2026-09-25):** the 10-second maximum between live/heartbeats and the long-pause regression passed. Review then found that a transient journal write/fsync failure could end the source task while leaving its timer and stale `live` status; a stop-time failure could interrupt shutdown. The local candidate now aborts the source, stops heartbeats, blocks `isLive()` even if the attention-store write also fails, and runs iterator/cursor/DB/server cleanup through nested `finally` blocks. Synthetic fault-injection tests cover connected, disconnect, stop, and combined journal/status-store failures; independent re-review returned PASS for this scoped fix. This does **not** authorize a VM shadow. A 360-heartbeat/30-minute synthetic sample occupied 91,024 bytes, leaving 40,048 bytes beneath the 128 KiB cap; reconnect storms or a pre-existing file can fill it early. Full must fail closed, not be treated as guaranteed 30-minute capacity. Exact x86_64 package review, rollback and VM CPU/RSS/write/fsync measurement remain separate authorization gates.

The comparator never prints identifiers, HMAC values, session names, prompts, request text, topic, credentials, paths or raw database errors. It prints only an enumerated verdict/reason, counts per kind, and timing statistics on PASS. It rejects malformed rows, duplicate request IDs in one path, more than 500 rows in the window, missing kinds and out-of-tolerance events. No input database is modified. Both paths' `eventId`s are intentionally different; matching uses kind, HMAC(session ID), HMAC(request ID) for the two request kinds, and one-to-one time matching. Repeated ready/task events in the same session lack a shared cross-path identity, so this proves bounded semantic parity, not identical upstream event identity; more than one possible time pairing returns `INDETERMINATE` for operator review.

## Authorization and decision boundaries

| Step | Authorization needed |
|---|---|
| Edit docs, run local fixtures and build a local comparator on synthetic databases | Covered by this task; no VM access |
| Start or resume alpha.9 on production VM, read private production snapshots/outbox, add temporary resources or run a new canary window | Separate, explicit VM shadow authorization with duration, resource/stop/restore scope |
| Create a real Runner canary session and generate ready/task/completion, or leave input/permission requests pending | Separate approval of those production user-facing actions; request handling needs the participant's cooperation |
| Change Nginx/public routes, enable Sidecar delivery, switch Mac/phone bindings, test native banners/ACK/replay and PWA clicks | Later, separate single-source cutover approval after complete Phase B |
| Retire the HAPI patch, change updater pin, upgrade Hub/Runner, migrate or roll back the production HAPI DB | Separate Updater and production release gate; never implied by Phase B |

If the five-kind canary passes, the next decision is whether to authorize **Phase C single-source cutover**. Phase C still requires real Mac banner/permitted sound, offline ACK/replay, OPPO notification/click and exact existing-window PWA navigation. If any kind remains unverified, continue isolated investigation or ask the product owner to explicitly revise the Phase-B requirement; neither the bounded first trial nor fixture coverage permits an automatic cutover.
