# HAPI Companion v0.2.0 — notification settings

Status: implementation candidate, not published or installed in production.

Implementation commit: `6d228a8`; review: [draft PR #1](https://github.com/creeep123/hapi-companion/pull/1).

## User-visible changes

Click the Companion menu-bar icon to open one native settings window. Reopening the app also focuses that window. Closing it leaves notifications running. The icon is retained explicitly and falls back to a system bell if the brand resource cannot load; crowded/hidden macOS menu bars still require local visual acceptance.

- Choose all conversations, or search and select real HAPI conversations. Selection follows session ID, so renaming keeps it selected.
- Add literal title keywords; any keyword or selected ID qualifies. Keywords also match new conversations. No AI task classification.
- Optionally skip tasks at or below a duration threshold in minutes. This is current foreground-turn duration; permission requests and events with unknown duration still notify.
- Schedule local quiet hours, including overnight: sound off or all notifications off. Equal start/end explicitly means all day. Quiet-period completions do not sound later on reconnect.
- Changes autosave locally per Hub. Existing users retain all reminders, with duration filtering and quiet hours initially off.
- Test reminder intentionally bypasses filters/quiet hours, and its button explicitly says it can play sound.

The approved design and the actual native window are in `docs/design/`. The actual screenshot is an isolated preview with clearly labelled fixture data, not a live Hub list or proof of production connectivity.

## Hub dependency

The cumulative reviewed patch in `integrations/hapi` adds an authenticated minimal conversation catalog and durable optional turn duration. It keeps schema v26, existing device authentication and one SSE connection. A legacy Hub still delivers notifications; unsupported catalog and unknown-duration behavior are explained in the window. Backend child tasks without their own timing evidence are not assigned the foreground task duration.

The patch is still tied to tiann/hapi@d3d4fd1706564782e9a58b917df4e0677f65051f. Do not apply the cumulative patch over an already patched production tree. Reconstruct a clean baseline candidate, review local production differences, test it and deploy only after operator approval. See `integrations/hapi/README.md`.

## Rollback

Before an approved local replacement, preserve the known-good v0.1 app bundle. The existing local installer re-pairs its device-scoped credential after replacement; this behavior is unchanged. Client rollback is restoring that prior app. V0.2 settings are stored under separate versioned keys and do not alter the v0.1 credential format.

Before an approved Hub replacement, record and retain its exact binary/container and database backup. V0.2 introduces no extra migration beyond the cumulative v0.1 patch's v26; rolling back across v26 still requires the corresponding pre-v26 database backup.
